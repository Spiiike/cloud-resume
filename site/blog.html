I built my resume on Azure with Terraform.
Here's everything that broke.

My resume now lives at glasscliff.online. The page runs on Azure, the infrastructure is defined in Terraform, and the visitor counter calls a Python API backed by Cosmos DB. A push to GitHub runs the tests before anything gets deployed.

That’s the finished version. Getting there involved a retired service, a subscription policy, a disappearing validation token, and a Python environment that wasn’t the one I thought I was using.

This was my Cloud Resume Challenge build. I used an Azure for Students subscription with $100 in credit, so cost wasn’t something I could leave until later. If the credit runs out, the subscription switches off. That constraint shaped a lot of the architecture.

This isn’t a walkthrough of every setup step. It’s a build log of the problems I actually ran into, what I changed, and what I’d check earlier next time.

The setup

The resume and API live in one Static Web App. Azure DNS handles the domain, the page calls /api/counter, and the function updates the count in Cosmos DB. GitHub Actions ships the application code; Terraform defines the infrastructure.

Browser → Azure DNS → Static Web Apps ├─ Resume page └─ /api/counter → Cosmos DB (Table API) GitHub Actions → tests → application deployment Terraform → Azure infrastructure

01 The tutorial was already out of date

The Azure version of the challenge starts with a Storage account behind Azure CDN. That sounded straightforward until I tried to build it. Azure CDN (classic) stopped accepting new profiles on August 15, 2025. The replacement I looked at, Front Door Standard, had a base fee of about $35 a month.

I had $100 in student credit. Spending more than a third of that every month to serve a resume wasn’t happening.

I went with Azure Static Web Apps on the Free plan instead. It hosts the page, handles managed TLS for the custom domains, and runs the Python API under /api. The page and API share an origin, so I didn’t have to add CORS configuration just to update a counter.

There were tradeoffs. Managed functions support HTTP triggers, which was fine for this project. There’s no managed identity for the managed API, so Terraform supplies the database connection string through an app setting. The plan allows two custom domains, which covered the apex and www.

NOTE TO SELF: Check whether the services in a tutorial are still available before planning the build around them.

02 A 403 sent me looking in the wrong place

My first terraform apply for the Static Web App failed with RequestDisallowedByAzure. My first instinct was to look at permissions. I owned the subscription, though, and this turned out to be a policy restriction rather than the RBAC problem I initially suspected.

Azure for Students had an “Allowed resource deployment regions” policy. South Central US was allowed by the subscription, but it wasn’t a region where I could deploy Static Web Apps. I needed a region that appeared on both lists: allowed by the policy and supported by the service.

I also had some cleanup to do around DNS. My DNS zone was in my default subscription, while the project was in the student subscription. I moved the zone into the project subscription so the Terraform configuration could use a single provider.

Then I got a “DNS zone not found” error. The zone had moved. My variables still named the old resource group.

NOTE TO SELF: Check policy as well as permissions. And when a resource moves, update the references—not just the resource.

03 Moving the old site without pulling the plug

glasscliff.online was already serving my portfolio from an App Service. I wanted the resume at the root, but I didn’t want to throw away the old site. The plan was to move it to projects.glasscliff.online and link to it from the resume.

This was mostly an exercise in doing things in the right order.

  1. I set up the portfolio’s new address first: the asuid TXT record for domain verification, a CNAME for projects, and a managed certificate.
  2. The certificate binding initially failed with an empty thumbprint. Certificate issuance was still happening in the background. I polled until the certificate existed, then bound it.
  3. I checked that the portfolio loaded at its new address before touching the apex.

When I finally went to move the apex, Terraform refused to create the A and CNAME records. Records with those names already existed.

Deleting them just so Terraform could recreate them would have interrupted the working site. Instead, I used terraform import to bring the existing records into state, then let the next apply change their targets.

NOTE TO SELF: Infrastructure as code doesn’t mean everything starts empty. Adopt the working resources before you replace anything.

04 The Terraform value that disappeared

This was probably the most interesting problem in the build.

Static Web Apps gives you a validation token to prove you own the domain. Terraform writes that token into a _dnsauth TXT record. The first apply worked. The next plan failed with an error about the expected length of record.0.value.

After domain validation succeeded, Azure cleared the token. My configuration was now trying to put an empty value into the TXT record.

I tried ignore_changes, but that wasn’t enough on its own. The expression still had to produce a valid value. Ignoring changes didn’t make an empty string valid.

The fix was to provide a fallback, then ignore changes to the record:

record {
  value = coalesce(
    azurerm_static_web_app_custom_domain.apex.validation_token,
    "validated"
  )
}

lifecycle {
  ignore_changes = [record]
}

The www domain had a different failure: CNAME Record is invalid.

I had typed the hostname into both the custom-domain resource and the DNS resource. The strings matched, but matching strings aren’t a Terraform dependency. Terraform could create both resources in parallel, which meant Azure could check for the CNAME before it existed.

I changed the custom-domain name to reference the DNS record directly:

domain_name = "${azurerm_dns_cname_record.www.name}.${azurerm_dns_cname_record.www.zone_name}"

That gave Terraform the dependency it needed to order the resources.

NOTE TO SELF: If one resource needs another, express that relationship in the configuration. Terraform can’t infer it from two strings that happen to match.

05 The failed apply that had actually created something

The counter uses a Cosmos DB account with the Table API in serverless mode. For this project, request-based billing made more sense than paying for capacity I wasn’t going to use.

The first apply failed with ServiceUnavailable. I treated it as a regional capacity issue and made the Cosmos region a separate variable, with East US 2 as the next region to try.

Before retrying, I checked Azure. Creating a Cosmos account is a long-running operation, and the CLI showed the account in a Succeeded state even though Terraform had reported a failure.

That changed the next step. Instead of blindly trying to create it again, I imported the existing account into Terraform state and applied again. The table and connection-string configuration followed.

NOTE TO SELF: A failed apply is not a rollback. Check what exists before assuming nothing happened.

06 My Python wasn’t the Python I thought it was

The API itself is small. A request to /api/counter reads the count, increments it, writes it back, and returns {"count": n}. The response includes Cache-Control: no-store so a cached response doesn’t stand in for the current count.

I kept the counter logic—next_count and bump—separate from the Azure Functions route handler. That let me test the logic with a fake table client instead of needing an Azure runtime or real credentials. The six unit tests ran in about 0.2 seconds.

Getting the right Python environment on Windows took longer than writing the tests.

  • python launched the Microsoft Store stub. py -3.11 found the interpreter I actually wanted.
  • My first virtual environment used Python 3.14 and resolved azure-functions to 2.3.0.
  • On Python 3.11—the runtime I was targeting in Static Web Apps—the dependency resolved to 1.25.0.

So I had passing local tests against a library version that wasn’t the one I would deploy. I pinned exact versions in requirements.txt and rebuilt the virtual environment on 3.11 to align local development, CI, and the deployment runtime.

Two calls to the live endpoint returned {"count": 4} and then {"count": 5}. The deployed counter was working.

There’s still a known limitation: the read-then-write operation isn’t atomic. Two simultaneous requests can read the same count and overwrite each other’s increment. The next fix is optimistic concurrency using the entity’s ETag, with conflict handling. For a cosmetic counter, I documented that limitation rather than expanding the first version.

NOTE TO SELF: “Works on my machine” includes the interpreter, not just the code. Match the runtime and pin the dependencies.

Shipping it: a failing test stops the deploy

One GitHub Actions workflow handles the site and API. It runs when a push or pull request touches the site, API, or tests.

  1. The test job installs the pinned dependencies on Python 3.11 and runs pytest.
  2. The deploy job declares needs: test. It uploads the site and API to Static Web Apps only after the test job succeeds.

The deployment token comes from a Terraform output and goes into a GitHub repository secret, not into the application code.

Still on the list

Terraform still runs from my laptop. Next is moving plan and apply into GitHub Actions with OIDC federation, so the workflow can authenticate to Azure without a stored cloud credential. After that, I’ll add ETag-based concurrency handling to the counter.

The biggest takeaway wasn’t a particular Azure service or Terraform command. It was learning to check what actually happened instead of taking an error message as the whole explanation.

The 403 wasn’t the permissions problem I expected. The failed apply had created a resource. The matching hostnames didn’t establish a dependency. In each case, looking at the policy, the live resource, or Terraform’s references was more useful than rerunning the same command.

If I were starting this again, I’d check service availability and subscription restrictions first, line up the Python environments earlier, and inspect Azure after a failed apply before trying anything else. Those checks would have saved me some unnecessary troubleshooting.

The finished resume is at glasscliff.online. The previous portfolio is at projects.glasscliff.online.
